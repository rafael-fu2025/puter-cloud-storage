## Puter Cloud Storage — project started

Workspace `C:\Users\udtoh_lmtzs7k\PuterCloudStorage` is now a Flutter Android
project (`puter_cloud_storage`), also a git repo pushed to
`github.com/rafael-fu2025/puter-cloud-storage` (private, branch `main`).

Goal: Android file manager using raf's Puter account as the storage backend.

### Hard constraint from raf

Auth must use a **Puter auth token**, not the OAuth/popup flow. Token is minted
at `puter.com/dashboard#account` → Create token. It is account-wide,
long-lived, non-refreshable, with no revocation push. Treated as a root
credential throughout: Keystore storage, redacting log interceptor, excluded
from Android auto-backup.

### Research findings that drove the design

See `docs/puter-api-research.md` for the full write-up.

- **Storage quota is 100 MiB on the free tier, not 310 GB.** raf believed the
  account has 310 GB. This is unverified and is the project's critical unknown.
  Phase 0 exists to settle it first. Flagged prominently in the README.
- **Puter exposes WebDAV that accepts the auth token as the password**
  (username `-token`). This is the architectural unlock — it gives pure-Dart
  streaming, `Range` resume and background transfers, with no WebView and no
  reverse-engineered endpoints. Became ADR 0002.
- **No Dart/Flutter SDK exists** for Puter. Every call is hand-built.
- **No server-side search** (no `fs.search()`), despite a search rate-limit
  bucket. Search must be client-side → the local index is core, not a cache
  (ADR 0003).
- **Uploads are not atomic** — a partial failure leaves earlier files written
  and is never rolled back → per-file transfer tasks, never batches (ADR 0004).
- **Rate limits are per-user-per-app**, plus a global 8,000 calls/min account
  ceiling. WebDAV adds 600 req/min and 10 concurrent, shared *per network* —
  the tightest constraint in the system.
- **WebDAV lockout trap**: 10 failed sign-ins in 15 min → 429 *even for the
  correct token*. So token validation is exactly one attempt, and no code path
  anywhere retries a failed authentication.
- `402` and `413` are not retryable; retrying changes nothing.

### Architecture

Transport abstraction with three implementations: `WebDavTransport` (primary),
`WebViewTransport` (Puter.js bridge, for what WebDAV cannot express — live
quota, signed URLs), `RestTransport` (undocumented, disabled). One contract
test suite is meant to run against all three.

Everything routes through a single `RequestScheduler`: per-class token buckets,
global concurrency cap, priority queue (interactive > visible > background),
full-jitter backoff, circuit breaker, and the auth-lockout guard.

`lib/core/` and `lib/domain/` are deliberately **Flutter-free** so they can be
verified with the Dart VM alone.

### Decisions worth remembering

- `AppConfig.maxConcurrentRequests` defaults to **5**, not 6. Five is the
  binding constraint (free tier allows 5 concurrent reads); a higher global cap
  would admit more reads than the read bucket permits. Caught by the
  verification script, not by review.
- Repo is **private** by default. raf did not specify; private is the safer
  default for an app holding an account-wide credential.
